# Joplin 충돌 알고리즘 심층 조사

Joplin Desktop **3.7.21** 공식 Windows 배포판 두 개를 분리된 프로필로 실행했다. REA 6.7.0으로 배포 JavaScript를 분석하고, 실제 renderer의 조건부 중단점에서 인자·조건·호출 스택을 기록했다. 새로운 동기화 엔진 기능은 구현하지 않았다.

**24회 실험(메타데이터 통제 17회 + API만 사용한 대조 실험 7회), 기록 검증 27개 통과, 실험 구간 중단점 기록 100개.** 이는 아래 시나리오에 대한 검증이며 Joplin 전체 동작을 보장하는 수치가 아니다.

핵심 결과:

1. 서로 다른 내용을 수정하면 먼저 동기화한 쪽이 원본으로 남고, 나중 쪽의 로컬 내용은 충돌 사본으로 보존됐다. 순서를 바꾸면 결과도 바뀌었다.
2. 업로드 충돌 후보는 `remote.updated_time > local.sync_time`으로 정한다. 로컬 수정 시각이 원격보다 최신인지로 승자를 고르지 않는다. 로컬 `updated_time`은 업로드 대상 선정에 영향을 준다.
3. 같은 제목·본문이면 내부 `noteConflict` 경로에 들어가도 충돌 사본은 생성하지 않았다.
4. 휴지통 이동과 영구 삭제는 다른 경로다. 영구 삭제를 나중에 동기화하면 먼저 업로드된 수정본도 새 충돌 사본 없이 제거됐다. 노트 기록을 통한 복구 가능성은 조사하지 않았다.
5. REA가 자동으로 완전한 호출 그래프를 복구하지는 못했다. 배포 번들·소스맵으로 위치를 좁히고 실제 Desktop 호출 스택과 실험으로 조건식을 검증했다.

`scripts/`는 조사용 하네스다. 엔진 구현이 아니며, 원본 전체 배포 코드나 사용자 프로필을 포함하지 않는다. 재현 명령은 이 디렉터리를 현재 디렉터리로 삼는다. `work/`는 실행 중 생성되는 비공개 임시 영역이다. 증거의 시각·검사 기록은 2026-10-23 로컬 조사 당시의 역사 기록이다.

저장된 기록만 검사하려면 이 디렉터리에서 `node scripts/conflict-verify.mjs --check`를 실행한다. Node 내장 모듈만 사용하며 파일을 바꾸지 않는다. CI도 이 명령을 사용한다. 실제 Desktop 실험을 다시 실행하는 절차는 위 재현 문서에 별도로 있다.
