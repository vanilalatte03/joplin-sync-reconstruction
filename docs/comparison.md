# 원본과 재구축 비교

> 이 문서의 아래 표와 가설은 초기 조사 당시의 기록으로 보존한다. 후속 조사에서는 반대 동기화 순서, 시각 경계, 편집/삭제 충돌, 동일 내용의 사본 억제를 확인했다. 현재 확인 범위는 [충돌 알고리즘 심층 조사](../investigation/conflict-algorithm/docs/conflict-algorithm.md)와 [엔진 차이 비교](../investigation/conflict-algorithm/docs/engine-comparison.md)를 참조한다. 다른 미검증 항목까지 해결됐다는 뜻은 아니다.

원본 실행은 공식 Joplin 3.7.21 / 파일 시스템 대상, 재구축은 Spring Boot / HTTP / H2다. 동일한 사용자 시나리오로 비교했지만 저장 포맷과 전송 프로토콜을 일치시키려 하지 않았다.

| 시나리오 | 원본에서 직접 관찰 | 재구축에서 실행 검증 | 차이·원인 가설·선택한 설계 |
|---|---|---|---|
| 생성 후 동기화 | `<id>.md` 생성, B가 같은 ID·본문 수신 | 서버 version=1, B가 ID·본문 수신 | 파일별 객체 저장 대신 중앙 HTTP 저장소를 사용했다. 논리 ID를 보존한다. |
| 수정 후 동기화 | 같은 원격 파일명 유지, B 본문 수정 | baseVersion 일치 시 version 증가, B 반영 | 원본 충돌 기준은 미규명이다. 재구축은 정수 버전을 명시한다. |
| 오프라인 편집 | B에서 동기화 호출을 보류해도 로컬 수정 유지; 원격은 이전 본문 | pending을 로컬 JSON에 저장; 클라이언트 재생성 뒤 내용 유지 | 원본 네트워크 격리는 미실시다. 재구축은 durable queue를 선택했다. |
| 상이한 동시 편집 | A→B 순서에서 B의 로컬 본문이 별도 충돌 노트로 보존되고 원래 ID는 A 본문 수신 | stale baseVersion에 409; 서버·B에 두 본문 보존, 정본은 기존 서버 내용 | 원본의 전체 판정 알고리즘은 미확인이다. 사용자가 내용을 잃지 않는 결과를 계약으로 삼았다. |
| 대상 접근 오류 후 재시도 | 파일 대상 경로를 동기화 전에 접근 불가능하게 만들고 복구한 뒤 수동 재동기화 성공 | 3회 실패 후 pending 유지, 새 클라이언트에서 재시도 성공 | 장애 계층과 타이밍이 다르다. 동일한 네트워크 장애를 검증했다고 주장하지 않는다. |
| 전송 중 실제 연결 유실 | **미검증** — 파일 시스템 대상 실험으로 네트워크 단절을 증명할 수 없다 | 서버 커밋 후 실제 HTTP 응답 소켓 파괴, 재요청 2회 이상, version=1·이력 1개 | 원본의 중복 방지 방식은 미확인이다. 재구축은 작업 UUID와 저장된 응답을 사용한다. |
| 기본 삭제 | `deleted_time>0`을 B에 전파, 원격 파일 존속 | deleted tombstone 전파 | 원본은 휴지통이 있다. 최소 엔진은 별도 휴지통 UX 없이 삭제 버전을 보존한다. |
| 영구 삭제 | 원격 파일 제거, B에서 API 404 | 자동 영구 삭제 없음 | 삭제 정보의 장기 안전성을 위해 tombstone을 영구 보존했다. 원본과 의도적으로 다르다. |
| 서버 재시작 | 이번 원본 실험에서 별도 DB 내구성 시험은 하지 않음 | 새 JVM에서 H2 전체 이력·cursor 동일 | 재구축 자체의 내구성 검증이다. 원본 대비 동등성을 주장하지 않는다. |

## 결과 범위

`evidence/original-scenarios/results.json`에는 기본 6개 관찰이 있다. 첫 항목은 최초 생성의 B 수신 확인이며, 접근 실패 항목에는 시작 전 장애라는 제한을 기록했다. 영구 삭제는 별도 `permanent-delete.json`에 있다. 원본의 인터넷 단절, WebDAV/S3, 자동 재시도 타이밍, 반대 동기화 순서, 편집/삭제 동시 충돌은 미검증이다.

`evidence/java-tests.txt`: 8 tests, 0 failures, 0 errors, 0 skipped.

`evidence/rebuild-demo.json`: 실제 HTTP와 클라이언트 파일을 사용한 8개 시나리오 통과. 원본의 여섯 시나리오 분류와 테스트 개수가 1:1로 대응하는 것은 아니다. HTTP 오류 입력과 conflict 조회 같은 재구축 검증이 추가돼 있다.

## 후속 확인이 필요한 가설

1. 원본에서 원격 객체의 수정 시각과 클라이언트의 마지막 동기화 정보를 조합해 충돌을 판단할 가능성이 있다. 이번 결과만으로 특정 필드나 비교식을 확정할 수 없다.
2. 영구 삭제를 장기 오프라인 클라이언트가 어떻게 발견하는지 확인하려면, 삭제 이전 기준을 가진 세 번째 격리 프로필로 재등장·부활 여부를 관찰해야 한다.
3. 원본의 전송 중 단절을 검증하려면 별도 로컬 WebDAV 테스트 서버와 결함 주입 프록시를 준비하고 요청 시작·중단·재시도 시각을 기록해야 한다. 기존 개인 계정이나 클라우드를 사용할 필요는 없다.

이 항목들은 미완료 분석이다. 재구축의 통과 결과로 원본의 미검증 동작을 채우지 않는다.
